# Operation and recovery

## Host-only GitHub App configuration

Register an App at <https://github.com/settings/apps/new> on the owner's account.
Disable webhooks and user OAuth/device flow. Grant only repository Contents
read/write, Pull requests read/write and implicit Metadata read. Install it for
only `luciferprosun/AIOA-spArkHAT-Meta-Hackathon-2026`.

Keep its generated private key outside the repository. Under the **existing**
Native state root, create `github-app/` owned by the Native user, mode 0700.
Place `private-key.pem` and `app.json` there, owner-only mode 0600, regular files
without hardlinks or symlinks. Never paste the key or installation token in Muse,
Mission Control, issue bodies, terminal output or logs.

`app.json` contains public identifiers only:

```json
{"schema":"aioa.github-app.v1","client_id":"PUBLIC_APP_CLIENT_ID","installation_id":123456789}
```

Use the actual local App's Client ID and installation ID. A connector-provided
installation ID is not a credential. Installation settings are available at
`https://github.com/settings/installations/<actual-installation-id>`.

Native validates private file permissions and signs a short-lived App JWT in
memory. Every new authorized operation requests a fresh narrowed installation
token and checks the visible repository set. No token cache or secret file is
created. No automatic permission expansion or CLI fallback exists.

## Three owner-submitted chat turns

Use the same Muse conversation. The owner submits each message and waits for a
completed result. No message is prefilled or automatically sent by this change.
For a repository factual answer, first deliberately refresh GitHub READ and
attach the resulting receipt; READ context expires after five minutes.

Use **Read code README at main SHA** for the canonical code repository, or
**Read demo README for Muse proposal** for the documentation repository. Each
recipe independently checks repository ID, main, commit/tree, regular README
blob bytes and main again. The signed result identifies `read_source`, commit,
tree, file hashes, receipt ID and observation time. The chat receives a clearly
marked excerpt of at most 1,536 UTF-8 bytes (also bounded after JSON escaping),
not a claim that the whole repository was read. The complete file is hashed;
files over 32 KiB, symlinks, missing files and main drift are refused.

Before the proposal turn, refresh the **demo** READ and explicitly attach it to
that message. Canonical-repository metadata or an earlier unattached chat turn
does not satisfy this requirement. Core resolves the original cached request,
canonical Meta receipt and signed READ; it compares the planning base/tree with
the independent demo preflight. A changed base requires a new deliberate READ
and a new model proposal. It never silently rebases the model's proposal.

1. Ask Muse to explain the verified repository READ, naming the exact main SHA
   and separating observation from inference.
2. Ask for a short implementation/design proposal. This is advisory text only.
3. Ask for one strict JSON proposal using the schema below, without Markdown
   fences or additional keys. Keep the file short enough for a complete reply.

Example of the required **shape**, not a fabricated model response:

```json
{"schema":"aioa.muse.github-change.v1","operation":"code.commit_draft_pr","target_repo":"luciferprosun/AIOA-spArkHAT-Meta-Hackathon-2026","files":{"agent-demo/owner-chosen-unique-name.md":"# Proposed demo note\n\nShort content generated by Muse.\n"},"title":"Add reviewed Muse demo note","body":"Proposed by Muse; exact change reviewed by the owner. No claim of tests unless actually run."}
```

Choose a **new filename** for each later demonstration. Existing files cannot be
overwritten. A truncated response is not eligible; ask Muse explicitly for a
smaller complete proposal. Validation never accepts a manually pasted substitute
for the recorded LIVE reply.

In GitHub tools, enter the completed chat request ID and validate it. The Core
will read the demo base and show the exact repository, branch, files/diff, SHA,
PR and blockers. Review everything before selecting the checkbox and approving.
The five-minute review is source- and owner-session-bound. It is not a reusable
session-wide GitHub permission.

Ending the source chat session, renewing the Native owner lease or changing the
source invalidates an outstanding review. LOCK/pagehide clears the chat text,
pending review and in-memory browser authority; late responses cannot restore
them. This does not cancel or erase already dispatched external effects.

Installation tokens are opaque and may use GitHub's longer, dot-separated 2026
stateless format. The adapter accepts that bounded format without decoding,
persisting or displaying it. Repository and permission narrowing are unchanged.
See [GitHub's installation-token guidance](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app).

## Results and recovery

Repeating a proposal request or its already bound Muse turn reads the saved
Core operation, even after the in-memory chat text expires. It does not repeat
preflight GETs, refresh the review or authorize another write.

- **Read saved Core result** and **Read authorization and saved operations** are
  local reads. They do not call Muse or GitHub and do not retry a mutation.
- While a worker runs, the panel polls only saved Core records.
- **Verify with GitHub GET** is an explicit external readback. It can recover
  evidence after restart or a lost response; it cannot continue partial writes.
- **STOP** cancels and revokes local authority. It does not delete remote objects.
- A receipt contains exact provenance, warrant and scope evidence, GitHub GET
  hashes, real commit/PR URLs, host signature and SHA256. These are historical
  observations, not a guarantee that nobody subsequently changed the repository.
- A 401, 403 or 429 is shown as an authentication, permission or rate-limit
  failure. Fix the underlying configuration before a future exact approval.
  Never manually replay an uncertain commit/PR with `gh` or curl.
- A missing reference or response is not proof of no effect. Keep UNKNOWN and
  its reservation. There is no automatic cleanup or rollback in this candidate.

No production deployment or acceptance may be called PASS on the basis of the
offline tests. Missing scoped credentials, prior unresolved liability or owner
approval must be reported as BLOCKED_EXTERNAL with the specific condition.
